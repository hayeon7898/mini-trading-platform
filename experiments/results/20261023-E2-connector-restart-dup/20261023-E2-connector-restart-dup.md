# E2. Debezium 커넥터 강제 종료와 중복 (장애 재현 실험)

> 로컬 Docker 환경에서 Kafka Connect를 강제 종료해 재현한 실험이다. 실서비스 장애 기록이 아니다.

## 요약

| 항목 | 결과 |
|---|---|
| 중복 발생 | 강제 종료(kill) 시 회당 1.4만~2.4만 건 재발행, 정상 종료(stop)는 **0건** |
| 중복 규모 | **마지막 오프셋 저장 이후 ~ kill 사이 발행량**과 일치 (오차 0~20%, 항상 초과 방향) |
| 정합성 | 본 실행 7회 모두 MySQL = ClickHouse `FINAL` (체결 건수·수량, 주문 상태별) → 중복은 `ReplacingMergeTree`가 흡수 |
| 복구 지연 원인 | 재기동 후 발행 재개까지 77~86초 중 약 75초가 **사용하지 않는 Debezium 커넥터 13종의 플러그인 스캔** |
| 조치 | 오프셋 저장 주기 60초 → 5초, 플러그인 경로를 MySQL 커넥터로 한정 → 회당 중복 평균 20,555 → 1,741건 (**−91%**), 재기동 → 재개 82.1 → 41.7초 (**−49%**) |

## 가설

| # | 가설 |
|---|---|
| H1 | Connect를 `docker kill`한 뒤 재기동하면 중복 이벤트가 생긴다 |
| H2 | 중복 건수는 "마지막 오프셋 저장 ~ kill" 사이 발행량과 같다 (0 ~ 저장 주기만큼) |
| H3 | 정상 종료(`docker stop`)는 종료 직전 오프셋을 저장하므로 중복이 없다 |
| H4 | 중복이 있어도 ClickHouse `FINAL` 결과는 MySQL과 일치한다 |

## 조건

| 항목 | 값 |
|---|---|
| 경로 | k6 → order-server(체결 시뮬레이터) → MySQL binlog → Debezium 3.6.2 → Kafka → ClickHouse |
| 부하 | 주문 150건/s × 180초 (CDC 이벤트 약 800~1,200건/s) |
| 장애 | 부하 시작 90초 후 `docker kill mts-connect`(또는 `docker stop -t 30`) → 15초 뒤 `docker start` |
| 기본 설정 | `offset.flush.interval.ms=60000`, `plugin.path=/kafka/connect` (Debezium 커넥터 13종) |
| 조치 설정 | `offset.flush.interval.ms=5000`, `plugin.path`를 MySQL 커넥터만 담은 폴더로 한정 |

| 지표 | 정의 |
|---|---|
| 실험 구간 | 부하 시작 전 ~ CDC 따라잡기 후의 토픽·파티션별 오프셋 범위 |
| 중복 | 실험 구간에서 **오프셋은 다른데 (토픽, 키, 메시지 원문)이 같은** 메시지. 같은 오프셋을 ClickHouse가 다시 읽은 경우는 제외 |
| 마지막 저장 | `connect-offsets` 토픽에 기록된 이 커넥터의 오프셋 메시지 타임스탬프 중 kill 직전 것 |
| 발행 재개 | 재기동 이후 첫 메시지의 Kafka 타임스탬프 |

중복 판정에 이슈의 `(id, __op, __source_ts_ms)` 대신 원문 전체를 쓴 이유: 주문은 같은 id가 정상적으로 여러 번 갱신되고 `source.ts_ms`가 같은 ms에 겹칠 수 있다. 재발행은 키·원문이 바이트 단위로 같다.

## 결과

### 기본 설정 (A)

| 회차 | 마지막 저장 후 경과 | 그 사이 발행량 | 중복 (체결 / 주문) | 합계 | 재기동 → 재개 | 장애 → 재개 | 대조 |
|---|---|---|---|---|---|---|---|
| kill r1 | 18초 | 14,345 | 5,700 / 8,623 | 14,323 | 85.9초 | 108.2초 | 일치 |
| kill r2 | 30초 | 21,247 | 9,530 / 14,045 | 23,575 | 83.0초 | 102.8초 | 일치 |
| kill r3 | 25초 | 19,733 | 9,900 / 13,868 | 23,768 | 77.3초 | 97.3초 | 일치 |
| stop r1 | — | — | 0 / 0 | **0** | 75.7초 | 98.9초 | 일치 |

- 중복 사본은 모두 2개
- 체결은 머지 전 행 수도 `FINAL`과 같음 → 중복이 이미 머지로 합쳐짐

### 조치 후 (B)

| 회차 | 마지막 저장 후 경과 | 중복 합계 | 재기동 → 재개 | 장애 → 재개 | 대조 |
|---|---|---|---|---|---|
| kill r1 | 2.2초 | 2,760 | 45.1초 | 65.9초 | 일치 |
| kill r2 | 1.4초 | 1,699 | 39.5초 | 59.5초 | 일치 |
| kill r3 | 0.8초 | 765 | 40.5초 | 62.2초 | 일치 |

| 지표 | A 평균 | B 평균 | 변화 |
|---|---|---|---|
| 회당 중복 | 20,555 | 1,741 | −91% |
| 재기동 → 재개 | 82.1초 | 41.7초 | −49% |
| 장애 → 재개 | 102.8초 | 62.5초 | −39% |

재기동 후 Connect 로그에 `Committing offsets for N acknowledged messages`가 5초 간격으로 찍혀 설정 반영을 확인했다.

### 시험 실행 (참고, 본 결과 제외)

`kill-r0`: 주문 300건/s 목표였으나 앞단 포화로 140건/s (응답 p95 7.9초). 중복 11,532건, 원본 시각 범위가 마지막 저장(16:45:40.6) ~ kill(16:46:27.0)과 정확히 겹쳐 H2를 처음 확인한 회차. 이후 부하를 150건/s로 낮춤.

## 해석

| 가설 | 판정 | 근거 |
|---|---|---|
| H1 | 채택 | kill 6회 모두 중복 발생 |
| H2 | 채택 (오차 0~20%) | 경과 시간이 짧을수록 중복이 적고(A·B 모두), A에서 중복이 그 사이 발행량의 99.8~120%. Connect는 저장 시점에 **ack를 받은** 레코드의 위치만 저장하므로, 그때 전송 중이던 레코드와 저장 시각보다 앞선 binlog 위치(시험 실행에서 약 1.6초 차이 관찰)만큼 더 재발행된 것으로 추정. 발행량 표본이 1~2초 간격이라는 측정 오차도 있음 |
| H3 | 채택 | 정상 종료는 남은 레코드를 보내고 오프셋을 저장한 뒤 내려감 |
| H4 | 채택 | 7회 모두 일치. at-least-once 소비를 전제한 `ReplacingMergeTree`(체결 id, 주문 버전) 설계가 중복을 흡수 |

### 복구 시간 분해

| 구간 | A (kill-r0 로그) | B (kill-tuned-r1 로그) |
|---|---|---|
| 플러그인 스캔 | 약 75초 (커넥터 13종을 하나씩 5~10초) | 약 18초 (MySQL 플러그인 약 12초 + 클래스패스 약 4초) |
| 워커 기동 → 그룹 합류·태스크 시작 | 수 초 | 약 7초 |
| 태스크 시작 → 발행 재개 | 약 7초 | 약 10~15초 (재기동 시각 기준 추정) |

B에서 남은 시간의 가장 큰 부분은 여전히 플러그인 스캔이다. 이 Kafka 버전의 기본 탐색 방식은 ServiceLoader 목록과 클래스 스캔을 둘 다 수행한다.

## 조치

| 조치 | 효과 | 절충 |
|---|---|---|
| `OFFSET_FLUSH_INTERVAL_MS=5000` | 최대 재발행 범위 60초 → 5초 분량, 회당 중복 −91% | `connect-offsets` 쓰기 12배 (메시지가 작아 부담 미미) |
| `plugin.path`를 MySQL 커넥터 전용 상위 폴더로 | 재기동 → 재개 −49% | 다른 커넥터를 추가하면 경로를 다시 늘려야 함 |

### 적용 중 발생한 문제

| 증상 | 원인 | 조치 |
|---|---|---|
| `CONNECT_OFFSET_FLUSH_INTERVAL_MS`가 반영되지 않음 (60000 그대로) | Debezium 이미지가 이 항목만 접두사 없는 `OFFSET_FLUSH_INTERVAL_MS`로 관리 | 변수 이름 변경 |
| 커넥터 `FAILED`: 태스크를 소스 커넥터로 인식 못 함 | `plugin.path`에 커넥터 폴더 자체를 지정해 안의 jar 32개가 각각 별개 플러그인 클래스로더로 로드됨 → Debezium 클래스가 갈라짐 | entrypoint에서 상위 폴더를 만들어 MySQL 폴더만 복사, 그 상위 폴더를 지정 |

## 한계

| 항목 | 내용 |
|---|---|
| 회차 | 조합당 3회 (stop은 1회) |
| H2 정밀도 | 저장된 binlog 위치(GTID)부터 kill까지의 이벤트를 직접 세지 않고, 0.5초 간격(실제 1~2초) 끝 오프셋 표본으로 비교 |
| 부하 | 150건/s 고정. 부하가 높을수록 같은 경과 시간에 중복이 비례해 늘어날 것으로 예상하나 미검증 |
| 장애 유형 | Connect 프로세스 즉사만 다룸. MySQL·Kafka 장애, 네트워크 단절은 미포함 |
| 남은 복구 시간 | B의 약 40초 중 플러그인 스캔 외 구간은 개선하지 않음 |

## 남은 과제

- `plugin.discovery=service_load`로 클래스 스캔 생략 시 복구 시간 (Debezium jar의 ServiceLoader 목록 지원 여부 확인 필요)
- Kafka Connect exactly-once 소스 지원(트랜잭션)으로 재발행 자체를 없애는 방식과 비교
- compose에 재시작 정책 추가 (실험 중에는 `docker kill` 후 자동 재기동이 실험을 방해해 넣지 않음)
