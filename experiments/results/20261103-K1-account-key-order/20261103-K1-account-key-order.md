# K1. 계좌 키 순서 보장 검증

07 스펙의 K1 실험 결과다.
로컬 docker compose 환경에서 수행한 검증 실험이다.
관련 이슈는 #62이고, 키 변경은 #61에서 적용했다.

## 가설

계좌 키로 바꾸면 한 계좌의 이벤트는 모두 한 파티션에 들어간다.
파티션 안에서는 이벤트가 DB 커밋 순서(binlog 순서)대로 놓인다.

## 해석

#### 계좌가 한 파티션에 모인 이유
- 같은 계좌의 메시지는 키가 같아 같은 파티션으로 해시된다.
- 변경 전에는 키가 행의 기본 키라 같은 계좌의 행이 여러 파티션에 흩어졌다.

#### 파티션 안 순서가 지켜진 이유
- 커넥터 태스크가 하나라 binlog를 읽은 순서대로 메시지를 보낸다.
- Kafka는 같은 파티션 안에서 받은 순서를 그대로 오프셋 순서로 저장한다.
- 파티션 전체에서 역전이 0이므로 계좌별 순서도 함께 보장된다.

#### 동률이 0인 의미
- 모든 메시지가 서로 다른 `(file, pos, row)` 값을 가졌다.
- 따라서 `__source_pos`는 트랜잭션 단위가 아니라 행 이벤트마다 다른 위치다.
- 07 스펙에서 착수 시 확인하기로 한 `source.pos`의 의미가 이것으로 확인됐다.

#### `id` 역전이 생기는 이유
- `id`는 `AUTO_INCREMENT`라 INSERT 시점에 정해진다.
- 체결 시뮬레이터가 같은 계좌의 주문을 동시에 처리하면, 먼저 `id`를 받은 트랜잭션이 더 늦게 커밋될 수 있다.
- 예시의 커밋 간격이 0~114ms로, 거의 동시에 처리된 트랜잭션에서 생겼다.
- 소비자가 `id`로 정렬하면 이 비율만큼 실제 커밋 순서를 뒤집는다.
    - 잔고 캐시(P3)나 계좌별 알림(P6)처럼 순서가 결과를 바꾸는 소비자에게는 무시할 수 없는 수치다.

## 관찰

#### 처리량 저하
- 목표 500 TPS에 대해 실제로는 364 TPS만 처리했다.
- 응답 p50이 2.2s로 느려 VU가 1000개까지 늘어도 요청을 제때 보내지 못했다.
- 체결 시뮬레이터는 초당 약 165건을 처리해 주문 접수를 따라가지 못했다.
- 원인 후보는 다음과 같다.
    - Docker 재시작 직후라 MySQL 버퍼 풀이 비어 있었을 수 있다.
    - 주문 약 477만 건, 체결 약 1670만 건으로 테이블이 커졌다.
    - 디스크가 가득 찼던 영향이 남아 있을 수 있다.
- K1 결론에는 영향이 없어 P7(주기적 응답 정지 분석)에서 함께 다룬다.

#### 스냅샷 메시지 규모
- 변경 후 구간에 스냅샷 메시지가 체결 11329574건, 주문 10624029건 있었다.
- #61에서 이름이 다른 커넥터가 새로 만들어지며 초기 스냅샷이 실행된 결과다.
- 주문 스냅샷이 주문 테이블 행 수의 두 배를 넘는다.
    - 태스크를 재시작했을 때 스냅샷이 처음부터 다시 시작된 것으로 보인다.
- 스냅샷 메시지도 계좌 키라 파티션 검사에는 포함했고, 순서 검사에서는 제외했다.

## 조치

- #61에서 적용한 계좌 키 설정을 유지한다.
- 순서가 필요한 소비자는 `id`가 아니라 오프셋 순서나 binlog 위치를 따른다.
    - P3, P6 스펙을 쓸 때 이 기준을 설계에 반영한다.
- 처리량 저하는 P7에서 1단계 500 TPS 결과와 비교해 원인을 찾는다.

## 원본 파일

`raw/` 폴더에 검사 도구의 출력을 그대로 남겼다.

| 파일 | 내용 |
|---|---|
| `boundary.txt` | 키 변경 경계 오프셋 |
| `key-order-mts-trading-executions.txt` | 체결 토픽 검사 요약 |
| `key-order-mts-trading-orders.txt` | 주문 토픽 검사 요약 |
| `key-order-*-id-inversions.csv` | `id` 역전 예시 (최대 100건) |

- 여러 파티션에 나타난 계좌 목록(`-multi.csv`)은 두 토픽 모두 0건이라 남기지 않았다.

## 재현 방법

```bash
(cd experiments/producer-tool && ./gradlew installDist)

docker run --rm -i --network mts_default -v "$PWD/load-test:/scripts" grafana/k6:2.3.0 run \
  -e RATE=500 -e DURATION=5m /scripts/orders.js

# 처리 대기 주문이 0이 된 뒤 실행
K1_DIR=experiments/results/20261103-K1-account-key-order
for t in mts.trading.executions mts.trading.orders; do
  docker run --rm --network mts_default \
    -v "$PWD/experiments/producer-tool/build/install/producer-tool:/app" \
    -v "$PWD/$K1_DIR/raw:/out" \
    eclipse-temurin:21.0.12.1_1-jre-noble /app/bin/producer-tool \
    key-order --topic "$t" --boundary /out/boundary.txt --out /out
done
```
