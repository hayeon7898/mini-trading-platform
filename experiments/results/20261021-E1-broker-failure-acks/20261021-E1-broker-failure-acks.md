# E1. 브로커 장애와 acks 설정 (장애 재현 실험)

> 로컬 Docker 환경에서 리더 브로커를 강제 종료해 재현한 실험이다. 실서비스 장애 기록이 아니다.

## 요약

| 항목 | 결과 |
|---|---|
| `acks=1` 유실 | 50,000 msg/s에서 3회 중 1회, **ack된 메시지 291건 유실** 재현. 5,000·20,000 msg/s 6회는 0건 |
| `acks=all` 유실 | 15회 모두 **0건** (`min.insync.replicas` 1·2 모두) |
| 멱등성 | 꺼짐: 6회 중 2회 중복(30·31건), 매회 순서 역전 96~117건 / 켜짐: 6회 모두 **중복 0, 역전 0** |
| 쓰기 중단 | 기본 설정 평균 22.3초 → 연결 설정 타임아웃 1초로 **9.5초 (57% 단축)**. 병목이 클라이언트 재연결 대기에서 컨트롤러의 장애 판정(세션 타임아웃 9초)으로 이동 |

## 가설

| # | 가설 |
|---|---|
| H1 | `acks=1`이면 리더가 복제 전에 죽을 때 ack된 메시지가 유실될 수 있다 |
| H2 | `acks=all`이면 리더가 죽어도 ack된 메시지는 유실되지 않는다 |
| H3 | ISR이 정상(3개)인 상태에서는 `min.insync.replicas` 1과 2의 결과가 같다 |
| H4 | 멱등성을 끄면 재시도로 중복·순서 역전이 생기고, 켜면 사라진다 |
| H5 | (실험 중 추가) 쓰기 중단이 리더 재선출보다 긴 것은 프로듀서가 죽은 브로커로 재연결을 기다리기 때문이다 |

## 조건

| 항목 | 값 |
|---|---|
| 클러스터 | Kafka 4.3.1 × 3 (KRaft combined mode), `unclean.leader.election.enable=false` |
| 토픽 | 회차마다 새로 생성, 파티션 1, RF 3, `--replica-assignment`로 리더를 **활성 컨트롤러가 아닌 브로커**에 고정 |
| 프로듀서 | `kafka-clients` 4.3.1, 일련번호 전송, 그 외 설정은 기본값 (`max.in.flight=5`, `linger.ms=5`, `delivery.timeout.ms=120000`) |
| 장애 | 전송 시작 후 `KILL_AT`초에 리더 `docker kill` → 전송 종료 후 `docker start` → ISR 3개 복구 → 검증 |
| 기본 부하 | 5,000 msg/s × 60초 (30만 건), 20초에 kill |
| 고속 부하 | 20,000 / 50,000 msg/s × 30초, 15초에 kill (`acks=1`만) |
| 검증 | 토픽을 high watermark까지 읽어 프로듀서의 ack 기록과 대조. **유실 = ack를 받았는데 토픽에 없음** |

| 지표 | 정의 |
|---|---|
| 쓰기 중단 (gap) | 연속된 ack 사이의 최대 간격. 장애 없을 때 기준선 102ms |
| 리더 감지 | kill 후 CLI 폴링으로 새 리더를 확인한 시각. 호출당 1~2초라 상한값으로만 사용 |

## 결과

### 조합별 (5,000 msg/s, 각 3회)

| acks | min.isr | 멱등성 | 유실 | 중복 | 순서 역전 | 쓰기 중단 평균 (범위) |
|---|---|---|---|---|---|---|
| 1 | 1 | X | 0, 0, 0 | 0, 0, 0 | 124, 99, 108 | 20.0초 (16.4~23.6) |
| all | 1 | X | 0, 0, 0 | 0, 0, **30** | 105, 96, 110 | 19.8초 (18.2~21.5) |
| all | 2 | X | 0, 0, 0 | 0, 0, **31** | 112, 117, 106 | 23.4초 (22.5~24.3) |
| all | 2 | O | 0, 0, 0 | 0, 0, 0 | 0, 0, 0 | 22.3초 (19.8~23.8) |

- 모든 회차 `failed=0`: 실패 응답은 없었고 프로듀서가 내부 재시도로 모두 성공시킴
- `failed_present=0`: 중복은 앱 재전송이 아니라 **프로듀서 내부 재시도**가 만든 것

### `acks=1` 고속 부하 (각 3회)

| 속도 | 전송 | 유실 | 순서 역전 | 쓰기 중단 평균 |
|---|---|---|---|---|
| 5,000 msg/s | 30만 | 0, 0, 0 | 99~124 | 20.0초 |
| 20,000 msg/s | 60만 | 0, 0, 0 | 387~446 | 37.5초 |
| 50,000 msg/s | 150만 | 0, **291**, 0 | 1,033~1,271 | 35.0초 |

유실 회차(`acks1-isr1-idemoff-rate50k-r2`) 상세:

| 확인 | 값 |
|---|---|
| 유실 오프셋 | 713,470 ~ 713,760 (291개 연속) |
| 유실 레코드 ack 시각 | kill 명령 +67~68ms (폭 1ms) |
| 토픽 끝 오프셋 | 1,499,709 = 1,500,000 − 291, 중복 0 |

### 쓰기 중단 원인 확인 (`acks=all`, `min.isr=2`, 멱등성 O)

| 조건 | 쓰기 중단 (3회) | 평균 |
|---|---|---|
| 기본값 (`socket.connection.setup.timeout.ms=10000`, max 30000) | 23.4 / 23.8 / 19.8초 | 22.3초 |
| `socket.connection.setup.timeout.ms=1000`, max 1000 | 9.7 / 9.5 / 9.5초 | **9.5초** |

기본값 회차(r1)의 시간 순서:

| kill 기준 | 사건 |
|---|---|
| 0 | 리더(브로커 3) `docker kill` |
| +0.16초 | 프로듀서 `Disconnected from node 3`, 메타데이터 갱신 요청 |
| 약 +9초 | 컨트롤러가 브로커 3을 장애로 판정, 새 리더 1 선출 (CLI는 +11.5초에 확인) |
| +23.5초 | ack 재개 |

## 해석

| 가설 | 판정 | 근거 |
|---|---|---|
| H1 | 채택 (조건부) | 리더는 로컬 기록 직후 ack하고 팔로워는 그 뒤에 가져간다. 그 사이에 죽으면 새 리더에 없는 꼬리가 생기고, 재기동한 옛 리더도 새 리더 기준으로 자기 꼬리를 버린다. 유실 291건이 연속 오프셋이고 kill 직전 1ms 안에 ack됐다는 점이 이 구조와 일치한다. 같은 Docker 호스트라 복제 지연이 ms 단위여서 5,000·20,000 msg/s에서는 꼬리가 거의 없어 재현되지 않았다 |
| H2 | 채택 | `acks=all`은 현재 ISR 전원이 기록한 뒤 ack하므로, ack된 메시지는 새 리더 후보 모두에게 있다 |
| H3 | 채택 | `acks=all`이 기다리는 대상은 전체 복제본이 아니라 **현재 ISR**이다. kill 시점 ISR이 3개였으므로 `min.isr`과 무관하게 ack된 데이터가 3대에 모두 있었다. `min.isr`은 ISR이 줄어든 상태에서 쓰기를 받을지 말지를 정하는 하한이라, 이 실험 조건에서는 차이가 드러나지 않는다 |
| H4 | 채택 | 멱등성이 없으면, 기록은 됐지만 응답을 못 받은 배치를 새 리더에 다시 보내 중복이 생기고, `max.in.flight=5`에서 앞 배치 재시도가 뒤 배치보다 늦게 들어가 순서가 바뀐다. 멱등성은 프로듀서 ID와 시퀀스 번호로 브로커가 중복을 거르고 순서를 강제한다. 순서 역전이 속도에 비례(약 100 → 400 → 1,100건)한 것도 재시도 대상 배치 수와 일치한다 |
| H5 | 채택 | 프로듀서는 0.16초 만에 끊김을 알았지만, 메타데이터 갱신 과정에서 사라진 브로커로 연결을 시도하고 응답 없는 주소라 연결 설정 타임아웃(10초)까지 묶였다. 타임아웃을 1초로 줄이자 쓰기 중단이 컨트롤러 판정 시간(9초)과 거의 같아졌다 |

## 조치

| 조치 | 전 | 후 | 비고 |
|---|---|---|---|
| `acks=all` | `acks=1`: 50,000 msg/s에서 291건 유실 | 유실 0 | 리더 기록 후 ISR 복제까지 기다리는 지연을 감수 |
| `enable.idempotence=true` | 중복 30·31건, 역전 약 100건 | 0, 0 | Kafka 3.0+ 기본값. `acks=all` 필수 |
| `socket.connection.setup.timeout.ms=1000` | 쓰기 중단 22.3초 | 9.5초 (−57%) | 지연이 큰 네트워크에서는 정상 연결도 끊길 수 있어 환경에 맞춰 조정 필요 |

남은 9.5초는 서버 쪽 `broker.session.timeout.ms`(기본 9초)가 결정한다. 줄이면 장애 판정이 빨라지지만, GC 일시 정지 같은 짧은 지연에도 정상 브로커를 장애로 오판할 위험이 커진다.

## 한계

| 항목 | 내용 |
|---|---|
| 환경 | 단일 호스트 Docker라 복제 지연이 실제보다 매우 짧음 → 유실 재현 빈도가 과소평가됨 |
| 장애 유형 | `docker kill`(프로세스 즉사)만 다룸. 네트워크 단절, 디스크 장애, 느린 브로커는 미포함 |
| 회차 | 조합당 3회라 확률적 현상(유실)의 빈도 추정에는 부족 |
| 리더 감지 | CLI 폴링 해상도 1~2초. 정확한 선출 시각은 브로커 로그 기준으로 확인 필요 |
| 컨트롤러 | combined mode에서 리더를 비컨트롤러 브로커에 두어, 컨트롤러 장애 조치가 겹치는 경우는 제외 |
| 고속 부하 | 20,000·50,000 msg/s에서 쓰기 중단이 35~38초로 더 긴 이유는 미검증 (연결 설정 타임아웃의 지수 증가와 재전송량이 겹친 것으로 추정) |
| 제외한 회차 | 시험 실행 r0, 실행 중 PC 절전으로 시계가 17시간 44분 점프한 `acks=1` r1 (재실행으로 대체) |

## 남은 과제

- ISR이 리더 하나로 줄어든 상태에서의 `min.insync.replicas` 1 vs 2 비교 (팔로워 복제 포트만 차단해 컨트롤러 쿼럼 유지)
- `broker.session.timeout.ms` 조정에 따른 쓰기 중단 변화
- `timeline.csv`로 장애 구간 처리량 그래프

## 재현

```bash
(cd experiments/producer-tool && ./gradlew installDist)
# 기본 조합
bash experiments/scripts/e1-run.sh <acks> <min_isr> <idempotence> <회차>
# 고속 부하
RATE=50000 DURATION=30 KILL_AT=15 TAG=rate50k bash experiments/scripts/e1-run.sh 1 1 false <회차>
# 연결 설정 타임아웃 단축
TAG=connto1s PRODUCER_CONFIG=socket.connection.setup.timeout.ms=1000,socket.connection.setup.timeout.max.ms=1000 \
  bash experiments/scripts/e1-run.sh all 2 true <회차>
```

`raw/<조합>-r<회차>/`: `run.log`, `meta.txt`, `producer.log`, `summary.txt`, `timeline.csv`, `verify-summary.txt`, `lost.csv`, `describe-*.txt`, `broker-N.log`, `isr.csv` (`acked.csv`, `failed.csv`는 용량 때문에 제외)
