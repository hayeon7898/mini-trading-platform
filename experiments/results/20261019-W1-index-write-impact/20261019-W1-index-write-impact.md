# W1. 조회 인덱스 추가의 쓰기 성능 영향

Q1에서 고른 `idx_orders_account_created (account_id, created_at)`가 주문 접수(쓰기) 처리량에 주는 영향과,
인덱스 DDL이 CDC 파이프라인에 주는 영향을 측정한다 (05 스펙 트레이드오프).

## 가설
- 주문 INSERT마다 보조 인덱스도 갱신되므로 처리량이 다소 줄고 응답 시간이 늘 것이다.
- 인덱스는 행 데이터를 바꾸지 않으므로 binlog 행 이벤트가 없고, CDC 토픽에 메시지가 생기지 않을 것이다.

## 조건
| 항목 | 값 |
|---|---|
| 환경 | 로컬 WSL2 Docker, MySQL 8.4.8 (메모리 1GB, 버퍼 풀 512MB), order-server 컨테이너 (풀 30, 시뮬레이터 켬) |
| 데이터 | `orders` 약 130만 건 이상 (실행마다 약 5만 건씩 증가) |
| 부하 | k6 2.3.0, 주문 접수 500 TPS 2분 (`load-test/orders.js`) |
| 공정성 | 매 실행 전 열린 주문(ACCEPTED, PARTIAL)이 0이 될 때까지 대기해 이전 실행의 체결 부하를 배제 |
| 순서 | 인덱스 없음 → 있음 → 없음 (순서 효과 확인용) |
| 절차 | `experiments/scripts/index-write-bench.sh` (1·2번), 3번은 같은 절차로 수동 실행 |

## 결과

### 쓰기 성능
| 순서 | 조건 | 처리량 | p50 | p95 | p99 | 건너뛴 요청 |
|---|---|---|---|---|---|---|
| 1 | 인덱스 없음 | 472/s | 235ms | 1.83s | 5.96s | 2,772 |
| 2 | 인덱스 있음 | 413/s | 2.03s | 3.55s | 4.46s | 9,051 |
| 3 | 인덱스 없음 | 407/s | 2.13s | 3.50s | 4.20s | 10,177 |

### CDC
| 항목 | 값 |
|---|---|
| 인덱스 생성 시간 (약 130만 행) | 8초 |
| DDL 전후 `mts.trading.orders` 메시지 수 (열린 주문 0, 다른 쓰기 없음) | 2,298,007 → 2,298,007 |

### 버퍼 풀
| 항목 | 값 |
|---|---|
| `innodb_buffer_pool_size` | 512MB |
| 테이블(PK) + 보조 인덱스 2개 | 약 210MB 이하 |
| `Innodb_buffer_pool_reads` (서버 시작 이후 누적) | 4,724 |

원본: `raw/`

## 해석
- **인덱스 하나의 쓰기 비용은 이 환경의 실행 간 편차보다 작아 구분되지 않는다.**
  인덱스가 없는 3번이 인덱스가 있는 2번과 거의 같다(407 vs 413/s, p50 2.13 vs 2.03s).
  1 → 2에서 느려진 것은 인덱스가 아니라 실행을 거듭하며 생긴 환경 변화로 보인다.
- **두 번만 쟀다면 잘못 결론 낼 뻔했다.** 1·2번만 보면 "인덱스로 처리량 12% 하락, p50 8.6배"가 된다.
  결과가 예상보다 커서 원인을 확인했고, 같은 조건을 다시 재서 순서 효과를 배제했다.
- **버퍼 풀 부족 가설은 기각.** 계좌 번호가 무작위라 보조 인덱스 삽입 위치가 흩어지므로,
  인덱스가 메모리에 안 들어가면 무작위 디스크 I/O가 생길 수 있다고 봤다.
  그러나 버퍼 풀(512MB)이 데이터 전체(약 210MB)보다 크고, 디스크 읽기는 누적 4,724회로 무시할 수준이었다.
- **인덱스 DDL은 CDC 이벤트를 만들지 않는다.** 다른 쓰기가 없는 상태에서 DDL 전후 메시지 수가 같다.
  인덱스는 행을 바꾸지 않아 행 이벤트가 없고, 스키마 변경 이벤트는 `include.schema.changes=false`로 꺼져 있다.

## 관찰 (범위 밖)
- 500 TPS 2분 부하 직후 열린 주문이 약 5만 건 쌓였고, 모두 체결되기까지 수 분이 걸렸다.
  부하 중에는 API 요청이 커넥션 풀을 대부분 차지해 시뮬레이터가 거의 체결하지 못한 것으로 보인다.
  실제 시스템이라면 "접수는 되는데 체결이 밀리는" 상황이다.

## 조치
- `idx_orders_account_created` 유지 (Q1의 조회 개선 효과가 뚜렷하고, 쓰기 비용은 측정 편차 이내).

## 남은 과제
- 실행을 거듭할수록 성능이 떨어지는 원인 확인 (테이블 증가, MySQL 내부 정리 작업, WSL 환경 등).
  원인을 통제한 뒤 같은 비교를 여러 번 반복해 편차 범위를 수치화
- 체결 시뮬레이터 전용 커넥션 분리 등으로 부하 중 체결 지연 개선
