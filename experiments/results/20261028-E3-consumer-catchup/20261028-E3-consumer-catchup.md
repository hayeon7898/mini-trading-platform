# E3. 컨슈머 중단 후 따라잡기 (장애 재현 실험)

> 로컬 Docker 환경(4코어)에서 재현한 실험이다. 실서비스 측정 기록이 아니다.

## 요약

ClickHouse의 Kafka 소비를 5분·20분 멈췄다가 재개하며, 부하가 계속 들어오는 중의 회복 과정을 측정했다.

- **유실 없음**: 본 측정 12회의 체결·주문 대조 24번이 모두 일치했다.
- **회복 시간을 정하는 것은 백로그 소진이 아니라 재개 직후 컨슈머 그룹 재조정 대기**였다. 5분치 백로그(약 23만 건)는 1~3초에 소진되는데, 기본 설정(`kafka_thread_per_consumer = 0`)에서는 5회 중 3회 약 16초 대기가 더해졌다.
- `kafka_thread_per_consumer = 1`에서는 대기가 한 번도 생기지 않아, 해소 시간 중앙값이 **18.2초 → 2.3초**가 됐다. 평상시 적재 지연(E0 벤치)은 차이가 없었다(p95 1,421 → 1,360ms). **운영 큐에 적용했다.**
- 준비 과정에서 **체결 적재가 경고 없이 영구 정지하는 경로**(일 단위 파티션, #49)와 **주문 큐 플러시 주기 누락**을 찾아 고쳤다.

## 배경

ClickHouse가 Kafka 소비를 멈추면(장애, 배포, 테이블 작업) 그동안의 체결·주문 이벤트는 Kafka에 쌓인다.
Kafka는 메시지를 보존하므로 유실은 없어야 하고, 재개 후 얼마나 빨리 따라잡는지가 운영상 회복 시간이 된다.

E4는 **미리 채운 전용 토픽을 새 메시지 없이 소진**하는 방식으로 최대 소비 처리량(21~23만 rows/s)을 쟀다.
E3는 **실제 운영 큐를 멈췄다 재개**하고, **재개 후에도 부하가 계속 들어오는 상황**에서 회복 과정을 본다.
해소 시간은 대략 `쌓인 양 ÷ (소비 속도 − 유입 속도)`이고, 여기에 재개 직후 컨슈머 그룹 배정 대기가 더해진다.

E4가 권장했지만 아직 운영 큐에 적용하지 않은 `kafka_thread_per_consumer = 1`을 실제 경로에서 검증하는 역할도 한다.

## 가설

| # | 가설 |
|---|---|
| H1 | 중단 중 쌓인 메시지는 유실 없이 모두 적재된다 (재개 후 MySQL과 ClickHouse 정합성 일치) |
| H2 | 중단 수 분 정도의 백로그는 소비 한계 대비 작아, 해소 시간은 **소진보다 재개 직후 그룹 재조정 대기가 지배**한다 |
| H3 | `tpc=1`(컨슈머마다 스레드)은 **재조정 대기를 없애** 해소 시간을 줄인다. 효과는 백로그 크기와 무관하다 |

> H3은 처음에 "중단이 길어질수록 적재 방식의 차이가 드러난다"(처리량 관점)였다. 시험 실행에서 대기의 원인이 재조정으로 드러나 고쳤다 (아래 "실험 전 발견" 4).
| H4 | 따라잡기 중 큰 묶음이 몰려도 ClickHouse 메모리 한도(약 1.8GiB)를 넘지 않는다 (01-executions.sql의 백필 메모리 이슈 재발 여부) |

## 조건

| 항목 | 값 |
|---|---|
| 호스트 | Docker 4코어, 8GB. 전체 스택이 같은 코어를 공유 |
| 부하 | k6 `orders.js` 80 TPS. 워밍업 1분 후 중단, 재개 후에도 lag 0까지 계속. 매 회차 열린 주문 0에서 출발 |
| 부하를 80으로 둔 이유 | 시뮬레이터는 초당 약 87건의 주문만 체결 처리(체결 유입 약 365/s ÷ 주문당 체결 4.2건). 300 TPS 1차 측정에서 열린 주문이 회차마다 2만 → 3만 → 13만 건으로 쌓여 출발 상태가 달라졌다. 체결 유입은 시뮬레이터 속도로 정해지므로 부하를 낮춰도 쌓이는 체결량은 거의 같다 |
| 중단 대상 | `mts.kafka_executions_queue`, `mts.kafka_orders_queue` (`DETACH TABLE` / `ATTACH TABLE`) |
| 변수 | 적재 방식 `kafka_thread_per_consumer` 0 / 1 × 중단 5분 5회, 중단 20분 각 1회 |
| 고정 | 파티션 6, `kafka_num_consumers = 3`, 묶음 10000, 두 큐 모두 `kafka_flush_interval_ms = 1000`, order-server 풀 30 (#45), compose 기동 (#46), 체결 테이블 월 파티션 (#49) |
| lag 측정 | `producer-tool lag`: Kafka Admin API로 1초마다 (토픽 끝 오프셋 − 그룹 커밋 오프셋). 그룹에 멤버가 없는 중단 구간도 조회됨 |
| 정합성 | 부하 종료 후 열린 주문 0, lag 0까지 기다린 뒤 `reconcile-executions.sh`, `reconcile-orders.sh` |

### 측정 지표

| 지표 | 정의 |
|---|---|
| 첫 소비 대기 | `ATTACH` → 커밋 오프셋이 처음 움직인 시각 |
| 해소 시간 | `ATTACH` → 두 토픽의 lag가 모두 0 근처(묶음 1개 이하)로 내려온 시각 |
| 따라잡기 소비 속도 | 첫 소비 → 해소까지 커밋 오프셋 증가량 ÷ 시간 |
| 메모리 최고치 | 따라잡기 구간 ClickHouse 컨테이너 메모리 최대 |
| 정합성 | `reconcile-executions.sh`, `reconcile-orders.sh` |

#### 첫 소비 대기 해석 시 주의할 점 (E5에서 발견)
- `e3-run.sh`는 체결 큐를 먼저, 주문 큐를 다음에 `ATTACH`한다.
- 먼저 붙은 큐가 1~2초 먼저 소비를 시작하므로, 체결과 주문의 첫 소비 차이 일부는 이 순서에서 생긴다.
    - `tpc=1` 80 TPS 5회 중 3회는 주문이 체결보다 약 1초 늦었고, 2회는 같았다.
    - 주문이 체결보다 먼저 소비를 시작한 회차는 없었다.
- 16초 대기처럼 큰 차이는 그룹 재조정 때문이며, 이 치우침으로 설명되지 않는다.

## 실험 전 발견

본 측정을 준비하며 시험 실행(중단 60초) 중에 찾은 것들이다. 4번은 실험 설계 자체를 바꿨다.

### 1. 일 단위 파티션 때문에 체결 적재가 경고 없이 멈춤 (#49에서 수정)

사전 정합성 대조에서 체결 약 10만 건이 ClickHouse에 없었다. Kafka 재생성(#46) 후 커넥터를 다시 등록하자
Debezium 전체 스냅샷이 CDC를 우회했던 시드(369일 범위)까지 보냈고, 묶음 1만 건이 100개 넘는 일 파티션에 걸쳐
`TOO_MANY_PARTS`로 거부됐다. Kafka 엔진은 커밋 없이 같은 위치를 재시도하며 수백만 번 다시 읽었다.
체결 테이블을 월 파티션으로 바꾸고(#49) 540만 건 재적재 후 일치를 확인했다. **따라잡기가 영원히 끝나지 않는 경로**였다.

### 2. kafka-exporter는 1초 lag 측정에 쓸 수 없음

부하 중에는 그룹 lag 지표가 대부분 빠지고(-1), 가끔 실제와 다른 0을 내보내 해소를 0.8초로 오판했다.
Kafka 도구(`kafka-consumer-groups.sh`)는 호출마다 JVM을 띄워 2~3초가 걸린다.
`producer-tool`에 Admin API 기반 `lag` 명령을 추가해 1초 해상도를 얻었다.

### 3. 주문 큐만 플러시 주기가 7.5초로 남아 있었음 (조치: 1초로 통일)

#30(E0)에서 체결 큐만 `kafka_flush_interval_ms = 1000`으로 줄였고 주문 큐는 기본값 7500ms였다.
수정 전후(`tpc=0`, 중단 60초) 주문 백로그 소진 구간(첫 소비 → 해소)이 **9.3초 → 2.0초**로 줄었다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 주문 첫 소비 | 16.6초 | 16.4초 |
| 주문 해소 | 25.9초 | 18.4초 |
| 소진 구간 | 9.3초 | 2.0초 |

처음에는 주문의 첫 소비 대기(16.6초)까지 플러시 주기 탓으로 봤으나, 수정 후에도 대기가 그대로이고
**체결 큐에서도 같은 16.4초 대기가 나타나** 별개 현상으로 분리했다 (4번).

### 4. 재개 후 16초 대기의 정체는 그룹 재조정 (실험 설계 변경)

브로커 로그(`tpc=0`, ATTACH 시점):

| 시각 | 일 |
|---|---|
| +0.000초 | 컨슈머 0이 빈 그룹에 합류 → 혼자 즉시 안정화, 파티션 6개 모두 배정 |
| +0.045초 | 컨슈머 1, 2 합류 → 재조정 다시 시작 |
| +15.5초 | 3명으로 안정화 |

컨슈머가 한꺼번에가 아니라 차례로 들어와 재조정이 두 번 일어나고, 두 번째는 이미 파티션을 가진 컨슈머 0이
다시 합류해야 끝난다. `tpc=0`은 스레드 하나가 컨슈머 셋을 돌아가며 처리하므로, 스레드가 아직 배정을 못 받은
컨슈머를 기다리는 동안 컨슈머 0의 응답이 늦어지는 것으로 해석했다. `tpc=1`로 같은 조건을 돌리자 대기가 사라졌다.

| (중단 60초, 1회씩) | `tpc=0` | `tpc=1` |
|---|---|---|
| 첫 소비 (체결/주문) | 16.4 / 16.4초 | 0.9 / 0.9초 |
| 해소 (체결/주문) | 19.4 / 18.4초 | 0.9 / 1.9초 |
| 메모리 최고 | 266MiB | 259MiB |

`tpc=0`의 대기는 합류 순서에 따라 갈려(다른 회차에서 체결 1.0초) 반복 측정으로 분포를 보기로 하고,
변수를 "중단 5분/20분 × 3회"에서 "중단 5분 × 5회 + 20분 × 1회"로 바꿨다.

### 5. 큐를 다시 만든 직후에는 약 42초 대기

큐를 재생성(DROP·CREATE)하면 예전 컨슈머가 그룹에서 나가지 않아, 새 컨슈머는 세션 만료(기본 45초)를 기다린다.
DETACH는 정상적으로 나간다("removing member"). 조건 전환(`e3-set-tpc.sh`) 후에는 60초 이상 기다린 뒤 측정한다.

### 1차 측정 (300 TPS) — 보조

시뮬레이터 처리량(초당 약 87주문)을 넘는 부하라 열린 주문이 회차마다 쌓였고(2만 → 13만 건), 주문 대조는 매번 불일치로 무효다. 체결 대조는 12회 모두 일치.
재조정 대기 패턴은 본 측정과 같았다.

| (중단 5분 × 5회) | `tpc=0` | `tpc=1` |
|---|---|---|
| 약 16초 대기 | **5/5회** | **0/5회** |
| 해소 중앙값 (늦은 쪽) | 22.3초 | 3.3초 |

중단 20분 `tpc=0`에서 첫 소비 70.3초가 나왔지만, PC가 약 하루 멈춘 직후 열린 주문 13만 건 상태에서 돈 회차였고 본 측정에서 재현되지 않았다(2.0초).

## 해석

| # | 가설 | 판정 | 근거 |
|---|---|---|---|
| H1 | 유실 없이 모두 적재 | **지지** | 본 측정 대조 24번 일치. 1차 측정 체결 대조 12번 일치 |
| H2 | 해소 시간은 소진보다 재조정 대기가 지배 | **지지** | 대기 없는 회차의 해소 2~5초, 대기가 생기면 그중 약 16초가 대기 |
| H3 | `tpc=1`은 재조정 대기를 없앤다 | **지지 (대기 제거에 한해)** | 대기 발생 `tpc=0` 8/10회(두 부하 합산) vs `tpc=1` 0/10회. 소진 속도 자체의 우위는 이 규모에서 뚜렷하지 않음 |
| H4 | 따라잡기 중 메모리 한도 이내 | **지지** | 최고 617MiB(1차 측정 포함), 한도 약 1.8GiB의 1/3. 50만 건 따라잡기 포함 |

**왜 16초인가.** 재개하면 컨슈머 셋이 한꺼번에가 아니라 차례로 그룹에 들어온다. 먼저 들어온 하나가 파티션 6개를 모두 받은 뒤 나머지가 들어오면 재조정이 한 번 더 필요하고,
이 재조정은 이미 파티션을 가진 컨슈머가 다시 합류해야 끝난다. `tpc=0`은 스레드 하나가 컨슈머 셋을 돌아가며 처리하므로, 아직 배정을 못 받은 컨슈머를 기다리는 동안 첫 컨슈머의 응답이 늦어진다.
합류가 우연히 한꺼번에 이루어지면 대기가 없다 — 그래서 결과가 "1~3초 또는 약 16초"로 두 갈래로만 나뉘었다.
`tpc=1`은 컨슈머마다 스레드가 있어 첫 컨슈머가 독립적으로 응답한다.

**E4와 다른 점.** E4는 `tpc=1`이 소비 처리량을 높인다고 했지만(미리 채운 토픽, 새 유입 없음), 두 큐가 동시에 따라잡고 부하도 들어오는 실제 경로에서는 처리량 차이가 뚜렷하지 않았다.
이 환경에서 `tpc=1`의 확실한 효과는 **회복 시간을 운에 맡기지 않게 하는 것**이다.

**E0의 미해결 관찰.** E0에서 "부하 시작 직후 약 30초 동안 지연이 몰린다"를 측정 절차(배정 완료 대기)로 우회했다. 큐를 재생성한 직후였으므로, 예전 컨슈머의 세션 만료 대기("실험 전 발견" 5)와 `tpc=0`의 재조정 지연이 겹친 것으로 설명된다.

## 조치

| 조치 | 내용 | 근거 |
|---|---|---|
| `kafka_thread_per_consumer = 1` 운영 적용 | init SQL 두 파일, 기존 환경용 마이그레이션 003 | 해소 중앙값 18.2초 → 2.3초, 평상시 지연·메모리 악화 없음 |
| 주문 큐 플러시 주기 1초 | init SQL, 마이그레이션 002 | 주문 소진 구간 9.3초 → 2.0초 ("실험 전 발견" 3) |
| 체결 테이블 월 파티션 | #49 | 과거 데이터 재적재 시 영구 정지 ("실험 전 발견" 1) |
| lag 측정 도구 | `producer-tool lag` | kafka-exporter는 부하 중 1초 측정 불가 ("실험 전 발견" 2) |

**알림 (#54에서 적용).** 관측한 정상 회복은 가장 길어도 20초 안팎(`tpc=0` 대기 포함 19.9초, 20분 중단 16.7초)이었다.
따라서 **"lag 1만 건 초과 + 2분간 커밋 없음"**이면 정상 회복이 아니라고 보고 Grafana 알림으로 만들었다. #49처럼 커밋 없이 같은 위치를 재시도하는 정지를 잡는다.
검증에서 60초 중단은 조용했고, 4분 중단은 3분 5초에 알림, 재개 35초 후 해제됐다.

## 한계

- 로컬 Docker(4코어, 8GB)에서 전체 스택이 같은 코어를 공유한다. 실서비스의 절대 수치가 아니다.
- 체결 유입(초당 약 330~365건)은 주문 부하가 아니라 체결 시뮬레이터 속도로 정해진다. 유입이 더 크면 소진 시간의 비중이 커질 수 있다.
- 중단 20분은 조건당 1회뿐이다.
- 16초 대기의 해석(스레드 하나가 컨슈머 셋을 돌봐 재조정 응답이 늦어짐)은 브로커 로그의 재조정 시각과 설정을 바꿨을 때 대기가 사라지는 것으로 뒷받침했을 뿐, ClickHouse 내부 동작을 직접 추적하지는 않았다.
- `kafka_num_consumers`를 1로 줄이는 것(재조정이 한 번뿐)도 대기를 없앨 수 있지만 비교하지 않았다.

## 원본 데이터 (raw/)

```
raw/
├── trial/                         시험 실행 (중단 60초, 300 TPS) — "실험 전 발견" 3·4의 근거
│   ├── 1-flush7500-tpc0/          주문 큐 플러시 7.5초 (수정 전)
│   ├── 2-flush1000-tpc0/          주문 큐 플러시 1초 (수정 후)
│   └── 3-flush1000-tpc1/          + kafka_thread_per_consumer = 1
├── rate300/                       1차 측정 (300 TPS, 열린 주문 누적으로 주문 대조 무효)
│   ├── tpc0/stop05m-r1~r5, stop20m-r1
│   └── tpc1/stop05m-r1~r5, stop20m-r1
├── rate80/                        본 측정 (80 TPS, 매 회차 열린 주문 0에서 출발)
│   ├── tpc0/stop05m-r1~r5, stop20m-r1
│   └── tpc1/stop05m-r1~r5, stop20m-r1
└── e0-recheck/                    tpc 0/1의 평상시 적재 지연 (E0 벤치마크, 80 TPS)
```

측정 순서는 trial → rate300 → rate80 → e0-recheck. 회차 폴더마다 `events.log`(단계 전환 시각), `lag.csv`(1초 lag 원본), `samples.csv`(단계·lag·메모리), `summary.txt`, `k6.log`, `reconcile-*.txt`가 있다.

## 재현

```bash
(cd experiments/producer-tool && ./gradlew installDist)   # lag 샘플러

bash experiments/scripts/e3-set-tpc.sh 0 && sleep 60       # 조건 전환 + 세션 만료 대기
for r in 1 2 3 4 5; do bash experiments/scripts/e3-run.sh 0 5 $r; done
bash experiments/scripts/e3-run.sh 0 20 1

bash experiments/scripts/e3-set-tpc.sh 1 && sleep 60
for r in 1 2 3 4 5; do bash experiments/scripts/e3-run.sh 1 5 $r; done
bash experiments/scripts/e3-run.sh 1 20 1
```

시험 실행은 `STOP_SEC=60 bash experiments/scripts/e3-run.sh <tpc> dry 0`.
