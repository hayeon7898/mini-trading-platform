## 배경

ClickHouse가 Kafka 소비를 멈추면(장애, 배포, 테이블 작업) 그동안의 체결·주문 이벤트는 Kafka에 쌓인다.
Kafka는 메시지를 보존하므로 유실은 없어야 하고, 재개 후 얼마나 빨리 따라잡는지가 운영상 회복 시간이 된다.

E4는 **미리 채운 전용 토픽을 새 메시지 없이 소진**하는 방식으로 최대 소비 처리량(21~23만 rows/s)을 쟀다.
E3는 **실제 운영 큐를 멈췄다 재개**하고, **재개 후에도 부하가 계속 들어오는 상황**에서 회복 과정을 본다.
해소 시간은 대략 `쌓인 양 ÷ (소비 속도 − 유입 속도)`이고, 여기에 재개 직후 컨슈머 그룹 배정 대기가 더해진다.

E4가 권장했지만 아직 운영 큐에 적용하지 않은 `kafka_thread_per_consumer = 1`을 실제 경로에서 검증하는 역할도 한다.

## 가설

| # | 가설 |
|---|---|
| H1 | 중단 중 쌓인 메시지는 유실 없이 모두 적재된다 (재개 후 MySQL과 ClickHouse 정합성 일치) |
| H2 | 500 TPS × 5분 정도의 백로그는 소비 한계 대비 작아, 해소 시간은 **소진보다 재개 직후 그룹 배정 대기가 지배**한다 |
| H3 | 중단이 길어져 백로그가 커질수록 적재 방식의 차이가 드러나, `tpc=1`이 해소 시간을 줄인다 |
| H4 | 따라잡기 중 큰 묶음이 몰려도 ClickHouse 메모리 한도(약 1.8GiB)를 넘지 않는다 (01-executions.sql의 백필 메모리 이슈 재발 여부) |

## 조건

| 항목 | 값 |
|---|---|
| 호스트 | Docker 4코어, 8GB. 전체 스택이 같은 코어를 공유 |
| 부하 | k6 `orders.js` 500 TPS. 워밍업 1분 후 중단, 재개 후에도 lag 0까지 계속 |
| 중단 대상 | `mts.kafka_executions_queue`, `mts.kafka_orders_queue` (`DETACH TABLE` / `ATTACH TABLE`) |
| 변수 | 적재 방식 `kafka_thread_per_consumer` 0 / 1 × 중단 시간 5분 / 20분, 조건당 3회 |
| 고정 | 파티션 6, `kafka_num_consumers = 3`, 묶음 10000, order-server 풀 30 (#45), compose 기동 (#46) |
| lag 측정 | 토픽 끝 오프셋과 컨슈머 그룹 커밋 오프셋을 1초 간격으로 직접 조회. kafka-exporter(5초)는 대시보드 그래프용 |

### 측정 지표

| 지표 | 정의 |
|---|---|
| 첫 소비 대기 | `ATTACH` → 커밋 오프셋이 처음 움직인 시각 |
| 해소 시간 | `ATTACH` → 두 토픽의 lag가 모두 0 근처(묶음 1개 이하)로 내려온 시각 |
| 따라잡기 소비 속도 | 첫 소비 → 해소까지 커밋 오프셋 증가량 ÷ 시간 |
| 메모리 최고치 | 따라잡기 구간 ClickHouse 컨테이너 메모리 최대 |
| 정합성 | `reconcile-executions.sh`, `reconcile-orders.sh` |
