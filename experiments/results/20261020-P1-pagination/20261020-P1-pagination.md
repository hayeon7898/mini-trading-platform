# P1. 주문 내역 페이지 이동 — OFFSET vs 커서

깊은 페이지에서 OFFSET 방식이 느려지는 것을 측정하고, 커서 방식과 비교한다 (05 스펙 3단계).

## 가설
- OFFSET: 앞의 N행을 읽고 버린 뒤 20행을 돌려주므로, 깊이 N에 비례해 느려질 것이다.
- 커서: 마지막 행의 `(created_at, id)`에서 바로 출발하므로, 깊이와 무관하게 일정할 것이다.

## 조건
| 항목 | 값 |
|---|---|
| 환경 | 로컬 WSL2 Docker, MySQL 8.4.8, order-server 컨테이너 (풀 30, **시뮬레이터 끔**) |
| 인덱스 | `idx_orders_account_created (account_id, created_at)` (Q1 채택) |
| 데이터 | 계좌 1의 최근 1년 주문 약 4.6만 건 |
| 요청 | `GET /accounts/1/orders?from=<400일 전>&size=20` + `page=깊이/20` 또는 `cursor=<깊이 직전 행>` |
| 측정 | 깊이마다 워밍업 2회 후 10회 호출, curl `time_total` 중앙값 |
| 동일성 확인 | 두 방식의 첫 주문 id 비교 |
| 절차 | `experiments/scripts/pagination-bench.sh` |

## 결과
| 깊이 (건너뛸 행) | OFFSET | 커서 | OFFSET / 커서 | 같은 첫 주문 |
|---|---|---|---|---|
| 0 | 31.6ms | 23.9ms | - (같은 쿼리) | yes |
| 1,000 | 25.0ms | 20.3ms | 1.2배 | yes |
| 10,000 | 64.5ms | 19.1ms | 3.4배 | yes |
| 40,000 | 195.5ms | 23.1ms | 8.5배 | yes |

원본: `raw/` (요약, 가장 깊은 OFFSET의 `EXPLAIN ANALYZE`)

## 해석
- OFFSET은 깊이에 비례해 느려진다. 인덱스로 정렬은 해결되지만, 건너뛸 행을 인덱스에서 하나씩 읽고 버리는 비용이 남는다.
- 커서는 깊이와 무관하게 약 20ms로 일정하다. `created_at <= 커서 시각`이 인덱스 범위의 상한이 되어, 건너뛸 행을 읽지 않는다.
- 깊이 0은 두 방식이 같은 쿼리인데도 약 8ms 차이가 난다. 이 정도를 측정 편차로 보면 1,000 깊이의 차이도 편차 범위이고,
  의미 있는 차이는 10,000부터다.
- 모든 깊이에서 첫 주문이 같아, 두 방식이 같은 위치를 돌려줌을 확인했다.
- 커서는 `created_at`이 같은 행이 여럿이어도 `id`로 이어진다. 같은 시각 주문을 3건씩 섞은 통합 테스트에서 50건을 7건씩 넘겨 누락·중복이 없음을 확인했다.

## 조치
- 주문 내역 API에 `cursor` 파라미터와 응답 `nextCursor` 추가 (권장 방식).
- `page`(OFFSET)는 비교용으로 남김. 실제 화면에서는 커서 방식 사용.

## 한계
- 계좌 1의 전체 주문이 약 4.6만 건이라 최대 깊이를 40,000으로 잡았다 (스펙 예시는 100,000).
- 단일 클라이언트 순차 호출이라 동시 부하에서의 차이는 측정하지 않았다.
