# E0. end-to-end 지연과 FINAL 대안 쿼리 비교

DB 커밋부터 ClickHouse 적재까지의 지연을 구간별로 측정하고, 중복을 다루는 집계 방식의 비용을 비교한다 (03 스펙).

## 가설
- #28에서 본 약 5초 지연은 Kafka 엔진이 메시지를 모았다가 일정 간격(`kafka_flush_interval_ms`, 기본 7.5초)마다 넣는 방식에서 온다.
  간격을 줄이면 Kafka→ClickHouse 구간만 줄고, DB→Kafka(Debezium) 구간은 그대로일 것이다.
- `FINAL`은 느리다는 통념대로 `argMax` 등 대안보다 비쌀 것이다.

## 조건
| 항목 | 값 |
|---|---|
| 환경 | 로컬 WSL2 Docker. ClickHouse 26.8.8.8 (메모리 상한 2GB), Kafka 브로커 3대, Debezium 3.6.2 |
| 부하 | k6 주문 접수 500 TPS 2분, 체결 시뮬레이터 켬. 측정 대상은 부하 중 커밋된 체결 |
| 공정성 | 실행마다 큐 재생성 → **파티션 6개 배정 완료 대기** → 열린 주문 0 대기 → 15초 → 부하 |
| 지연 구간 | `source_ts`(MySQL 커밋, Debezium `source.ts_ms`), `kafka_ts`(Kafka 엔진 `_timestamp_ms`), `ingested_at`(ClickHouse 적재) |
| `kafka_ts`의 의미 | 체결 토픽의 시각 기준이 기본값 `CreateTime`이라 **Connect가 메시지를 만든 시각**. 따라서 DB→Kafka = Debezium 읽기·메시지 생성, Kafka→CH = 브로커 전송 + ClickHouse 소비·묶음 대기 |
| FINAL 비교 | 같은 집계를 방식별로 5회 실행해 중앙값, 쿼리 결과 캐시 끔 |
| 절차 | `experiments/scripts/e2e-latency-bench.sh`, `experiments/scripts/final-vs-alternatives.sh` |

## 해석

### 지연은 ClickHouse의 묶음 간격이 좌우한다
- DB→Kafka는 모든 조건에서 p95 약 0.5초로 일정하다. Debezium은 병목이 아니다.
- Kafka→CH의 p50은 묶음 간격의 약 절반~2/3, p95는 묶음 간격 + 0.5~1초 수준이다. 메시지가 묶음 대기 중 임의의 시점에 도착하기 때문이다.
- 간격을 7.5초 → 1초로 줄이자 전체 p95가 7.6초 → 1.7초가 됐다.

### 꼬리 지연 20~30초의 원인은 측정 절차였다
- 처음 측정에서 p95·p99가 묶음 간격과 무관하게 20~30초였다. 10초 단위로 보니 큰 지연은 매번 부하 시작 직후 약 30초에만 몰렸고, 평상시와 부하 후 대량 처리 중에는 묶음 간격 수준이었다.
- 가설을 차례로 확인했다.
  - 메모리 한도: 메모리 사용 25%, 오류 카운터는 서버 시작 이후 누적값이라 근거 부족
  - Connect 전송 지연: Kafka→CH 구간에서 생긴 지연이라 해당 없음
  - 파트 과다: `DelayedInserts` 0
  - **컨슈머 그룹 리밸런스**: `system.text_log`에서 지연 구간 동안 컨슈머 3개 모두 `No assignment`, `Can't get assignment` 반복. 바로 직전에 스크립트가 큐를 다시 만들어 새 컨슈머가 그룹에 합류한 기록 확인
- 스크립트가 큐를 다시 만든 지 15초 만에 부하를 시작했는데, 파티션 배정에는 45초가 걸렸다. 그 사이 커밋된 체결이 배정 후 한꺼번에 들어가며 꼬리 지연이 됐다.
- 배정 완료를 기다리도록 고치자 p95가 21초 → 1.3초로 정상화됐다.
- 운영 관점의 의미: **Kafka 엔진 테이블을 다시 만들면(스키마·설정 변경) 약 45초 적재가 멈춘다.** 45초는 컨슈머 그룹 기본 세션 타임아웃과 같아, 사라진 옛 컨슈머가 그룹에서 정리되기를 기다린 시간으로 보인다.

### FINAL이 대안보다 빨랐다
- 통념과 달리 `FINAL`이 `argMax`보다 4~15배 빨랐다. 정렬 키가 `id`라 `FINAL`은 정렬된 데이터를 읽으며 인접한 같은 `id`만 비교하면 되지만,
  `argMax ... GROUP BY id`는 수백만 개 `id`를 해시 테이블에 올려 묶어야 한다.
- 중복 제거 없이 세면 주문 테이블에 이미 끝난 주문의 이전 상태가 섞여 "미체결 9만 건"처럼 틀린 숫자가 나온다.
- 한계: 머지가 대부분 끝난 상태, 약 260만·70만 행 규모에서의 결과다. 파트가 많이 쌓인 상황에서는 `FINAL` 비용이 달라질 수 있다.

## 조치
- `kafka_flush_interval_ms` = 1000. 500ms(p95 1.3초)보다 0.4초 느리지만 초당 삽입 횟수가 절반이라, 작은 파트와 머지 부담을 줄이는 절충.
- 정확한 집계는 `FINAL` 사용.
- 측정 스크립트는 큐 재생성 후 파티션 배정 완료를 기다림.

## 남은 과제
- 체결 토픽을 `LogAppendTime`으로 바꿔 브로커 전송 시간을 DB→Kafka 쪽으로 분리
- Kafka 엔진 테이블 재생성 시 적재 중단(약 45초)을 줄이는 방법 (세션 타임아웃 조정 등)
- 파트가 많이 쌓인 상황에서 `FINAL` 비용 재측정
