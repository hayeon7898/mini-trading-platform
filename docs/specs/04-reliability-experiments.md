# 04. 장애·부하 실험

## 목적

장애를 직접 주입하고 결과를 수치로 검증해, 분산 메시징 시스템의 내구성·가용성 설정이 실제로 어떻게 동작하는지 확인한다.

> 모든 실험은 운영 환경이 아닌 로컬에서 재현한 "장애 재현 실험"임을 결과 문서에 명시한다.

## 모니터링 준비

- kafka-exporter: 컨슈머 그룹별·파티션별 lag, ISR 수, Under-replicated partitions
- Grafana 대시보드(`infra/grafana`): 토픽 유입, 컨슈머 소비 속도, 컨슈머 lag, URP, order-server p95·HikariCP
- Grafana 알림 "ClickHouse 적재 정지": lag 1만 초과 + 2분간 커밋 없음 (#54, 기준은 E3 결과)
- 범위에서 뺀 것 (#42)
  - Kafka JMX exporter: URP·ISR은 kafka-exporter로 수집 중이라 제외. 브로커 바이트 처리량·ISR 축소 비율이 필요한 실험이 생기면 추가
  - end-to-end 지연 패널: ClickHouse 데이터소스 플러그인이 필요해 제외. 지연은 `experiments/scripts/e2e-latency-bench.sh`로 측정

---

## E1. 브로커 장애와 acks 설정 (최우선)

**가설**: `acks=1`이면 리더 브로커가 복제 전에 죽을 때 메시지가 유실될 수 있고, `acks=all` + `min.insync.replicas=2`면 유실이 없다.

**방법**
- `experiments/producer-tool`: 일련번호(1, 2, 3...)를 붙여 메시지를 보내는 단순 Java 프로듀서. acks 설정을 인자로 받는다.
- 전송 중 해당 파티션 리더 브로커를 `docker kill`
- 검증 컨슈머가 처음부터 읽어 일련번호 누락·중복을 카운트

**조합**

| acks | min.insync.replicas | 예상 |
|---|---|---|
| 1 | 1 | 유실 가능 |
| all | 1 | 리더 단독 ISR이면 유실 가능 |
| all | 2 | 유실 없음, 대신 브로커 2대 죽으면 쓰기 실패 |

**기록**: 누락·중복 건수, 리더 재선출 소요 시간, 프로듀서 에러 로그.
유실 재현이 잘 안 될 수 있다. 그 경우 "왜 재현이 어려웠는가"도 그 자체로 좋은 기록이다.

추가 확인: `enable.idempotence=true`일 때 재시도로 인한 중복이 사라지는지.

## E2. Debezium 커넥터 재시작과 중복

**가설**: 커넥터를 강제 종료 후 재시작하면 마지막 커밋된 오프셋 이후부터 다시 읽으므로 일부 이벤트가 중복 발행된다.

**방법**: 부하 중 Connect 컨테이너 `docker kill` → 재기동 → 토픽 내 같은 (id, op, source.ts_ms) 이벤트 수 집계.

**기록**: 중복 건수, ClickHouse `FINAL` 결과가 여전히 MySQL과 일치하는지.

## E3. 컨슈머(ClickHouse) 중단 후 따라잡기

**가설**: 소비가 멈춰도 Kafka에 데이터가 보존되므로 재개 후 lag가 해소된다. 해소 시간은 쌓인 양과 적재 방식(`kafka_thread_per_consumer`)에 좌우된다.

**방법**: 운영 큐(체결·주문 Kafka 엔진 테이블)를 `DETACH` → 80 TPS 부하 N분 → `ATTACH` 후 lag가 0이 될 때까지 1초 간격으로 측정. 부하는 재개 후에도 계속 넣어, 유입이 이어지는 중의 따라잡기를 본다.

- 변수: 적재 방식(현재 `kafka_thread_per_consumer=0` / `1`) × 중단 5분 5회, 중단 20분 각 1회
  - 시험 실행에서 해소 시간을 정하는 것이 백로그 크기가 아니라 재개 직후 그룹 재조정 대기이고, 그 대기가 회차마다 달라 반복 횟수를 늘렸다 (#43)
- 측정: 재개 → 첫 소비까지 대기, 재개 → lag 0까지 시간, 따라잡기 구간 소비 속도, ClickHouse 메모리 최고치, 재개 후 MySQL과 정합성
- 컨슈머 수에 따른 소비 처리량은 E4에서 측정했으므로 변수에서 뺐다 (#43). E3는 E4의 미적용 권장안(`tpc=1`)을 실제 운영 큐에서 검증하는 역할도 한다

## E4. 처리량 한계와 파티션 수

**가설**: 파티션 수가 소비 병렬도의 상한이므로 늘리면 처리량이 오르지만, 일정 수준 이후엔 다른 병목(DB, 디스크)이 드러난다.

**방법**: 파티션 3 / 6 / 12, k6로 TPS를 단계적으로 상승 → lag가 계속 쌓이기 시작하는 지점과 지연 p95 측정.

**기록**: 표와 그래프. 병목이 어디였는지(order-server, MySQL, Debezium, ClickHouse) 근거와 함께.

## E5. 핫 파티션

**가설**: 특정 종목에 트래픽이 몰리면 키 분포가 쏠려 특정 파티션만 lag가 쌓인다.

**방법**: 종목 키 기반 토픽(2단계에서 키 재설정 후)으로 상위 1개 종목에 트래픽 50% 집중 → 파티션별 lag 비교.

> **2단계로 이동.** 메시지 키가 PK(Debezium 기본)라 종목 쏠림이 파티션에 나타나지 않는다. 06 스펙 P2(키 재설계)와 함께 진행한다.
> 파티션별 lag는 Grafana 대시보드(#42)와 `producer-tool lag`(#43)로 관찰할 수 있게 준비해 두었다.

---

## 우선순위

**E1 → E4 → E2 → E3 → E5** 순으로 진행한다. E1(내구성)과 E4(처리량)가 파이프라인 설계 검증의 핵심이다.

## 결과 요약

모두 로컬 Docker(4코어, 8GB)에서 재현한 장애 재현 실험이다. 상세는 각 결과 문서.

| 실험 | 결과 | 조치 |
|---|---|---|
| E1 브로커 장애와 acks | 리더 강제 종료 시 `acks=1`은 50,000 msg/s에서 ack된 메시지 **291건 유실** 재현, `acks=all`은 15회 모두 **0건**. 멱등성을 끄면 중복·순서 역전, 켜면 0 | 연결 설정 타임아웃 1초로 쓰기 중단 22.3초 → 9.5초 |
| E2 커넥터 재시작과 중복 | 강제 종료 시 회당 1.4만~2.4만 건 재발행(정상 종료는 0), 정합성은 `ReplacingMergeTree`가 흡수해 7회 모두 일치 | 오프셋 저장 주기·플러그인 경로 조정으로 중복 **−91%**, 재개 시간 **−49%** |
| E3 컨슈머 중단 후 따라잡기 | 유실 없음(대조 24번 일치). 회복 시간은 백로그 소진(1~3초)이 아니라 **재개 직후 재조정 대기(약 16초, 5회 중 3회)**가 지배 | `kafka_thread_per_consumer = 1`로 해소 중앙값 **18.2초 → 2.3초**, 주문 큐 플러시 1초 통일, 적재 정지 알림(#54) |
| E4 처리량과 파티션 수 | 파티션 3 → 6 → 12에서도 최대 소비 21~23만 rows/s로 같음. 기본 적재 방식은 컨슈머를 늘릴수록 15.7만 → 7.9만으로 감소 | 실제 경로(약 2,200 events/s) 대비 약 100배 여유 → 병목은 앞단(order-server·MySQL) |
| E5 핫 파티션 | 2단계로 이동 (06 P2 후) | — |

준비·측정 과정에서 찾은 운영 문제: 체결 테이블 일 단위 파티션으로 인한 적재 영구 정지(#49), Kafka 재생성 시 데이터 초기화와 재스냅샷(#46). 같은 정지가 다시 생기면 알림(#54)으로 감지한다.
